# Integración con backend — contrato vigente en el repositorio

El frontend usa server actions y llamadas `fetch` desde código `server-only`; no hay API route/BFF adicional. Base configurada mediante `API_URL`, variable obligatoria solo del servidor (localmente: `http://localhost:8081`). Ver [API backend](../../../adoptr-back/docs/arquitectura/api.md) para respuestas y limitaciones reales.

## Sesión y modelos

- Google entrega **ID token** al callback cliente. El frontend lo envía al backend mediante server action. Backend devuelve **JWT Adoptr** distinto; `setAccessToken` lo guarda HttpOnly/SameSite Strict/Secure. `loginAction` devuelve al cliente solo `{ hasProfile }` para decidir la redirección (lo que retorna una server action llega al navegador, y el JWT solo debe vivir en la cookie) y el callback no registra la respuesta de Google. Si el login falla, la página muestra un mensaje genérico sin detalles internos. Al agregar server actions, no devolver tokens ni datos que el componente no necesita. `apiRequest` lee cookie en servidor y agrega Bearer solo si hay token; con `requiresAuth=true` sin cookie no detiene la petición.
- Server actions con datos del usuario (`actions/profile.ts`, `actions/location.ts`): devuelven un resultado (`{ ok: true }` o `{ ok: false, code }`) en vez de lanzar el error, para que el componente pueda decidir por `code`. `createProfileAction`, ante `UNAUTHENTICATED`, borra la cookie y redirige a `/login`; la búsqueda de localidades solo devuelve `{ ok: false }` y el selector muestra un error. Las páginas de servidor, ante `UNAUTHENTICATED`, solo redirigen, porque no pueden borrar cookies. Arman el body con los campos esperados en vez de reenviar lo que llega del navegador.
- Backend configura expiración JWT de 1 h; la cookie no tiene TTL explícito. `proxy.ts` solo mira presencia, no expiración ni revocación. Una solicitud posterior puede recibir 401/otro error; tratar estado de sesión y redirección de forma coherente al implementar datos protegidos.
- Modelos (`src/lib/api/models/`) alineados con el contrato: IDs `Long` como `number`; `createdAt` como cadena ISO; `User.profile` puede ser `null` (el usuario todavía no creó su perfil); `Profile` es una unión discriminada por `profileType` (`PERSON` con `firstName`, `lastName`, `genderType`; `ORGANIZATION` con `organizationName` y redes opcionales) y el body de `POST /profile` es `CreateProfileInput`; `Locality` trae `id`, `name` y `displayName` (mostrar siempre `displayName`), y la provincia del perfil viene aparte en `province`. La forma de error backend es `{code:string,message:string}` en **todos** los errores, incluidos los 401/403 de Spring Security. `code` es un texto estable y único en toda la API (`UNAUTHENTICATED`, `PROFILE_NOT_FOUND`, `VALIDATION_ERROR`, …; tabla completa en [API backend](../../../adoptr-back/docs/arquitectura/api.md)): decidir por status + `code`, nunca por el texto de `message`.
- Fotos de adopción: el alta no es atómica. Primero `POST /adoptions` y después un `POST /adoptions/{id}/photos` por archivo, en orden y de a uno (el back las numera según llegan y la primera es la portada). Van del navegador a una server action y de ahí al back, porque el JWT y `API_URL` solo existen en el servidor y producto pidió no subir directo a S3; por eso `experimental.serverActions.bodySizeLimit` es `6mb` en `next.config.ts` (igual que `max-request-size` del back; el límite por defecto de `proxyClientMaxBodySize`, 10 MB, alcanza). Si una foto falla, la publicación ya existe: `adoption-form.tsx` guarda el id y reintenta solo las que faltan, sin volver a crearla. Las imágenes se muestran con `next/image` `unoptimized`, sin `remotePatterns`, porque el back ya las reduce a 1600 px y su host depende del entorno (bucket o CDN). El back debe tener la API de fotos: sin `photos` en la respuesta el detalle falla.
- `src/lib/api/api.ts` devuelve `{ data, headers: { totalCount, contentType } }` para status 2xx; no hay contrato de paginación implementado ni header `x-total-count` emitido por controllers actuales. No fija timeout/cache. Ante una respuesta de error lanza `ApiError` con `status`, `code` y `message` del cuerpo `{ code, message }` del back; si el cuerpo no tiene ese formato (proxy, caída, HTML), `code` es `UNKNOWN_ERROR`. No registra el cuerpo del error. `ApiError` solo existe en el servidor: una server action que necesite informar el motivo al cliente debe devolver el `code` en su resultado en vez de relanzar el error, porque en producción Next.js oculta el mensaje de los errores que cruzan al cliente. Pendientes: unificar la estrategia de 401 (hoy cada server action y página la resuelve como se describe arriba), errores de red/timeout (hoy `fetch` los lanza sin envolver) y caché privada.

## Regla de sincronización y salida

Cuando cambie una ruta backend, revisar [contrato HTTP](../../../adoptr-back/docs/arquitectura/api.md), modelos TS, permisos, errores y prueba de integración en el mismo cambio. No consumir como funcional un stub ni un service interno; documentar por separado **observado**, **bloqueado** y **propuesto**. Para desplegar login se requiere cerrar los bloqueos del backend (validación de identidad y rotación del secreto), comprobar que el JWT Adoptr nunca se serializa al navegador y que el ID token Google solo se usa en el callback y envío a la server action, sin aparecer en logs. Configurar `API_URL` según dónde corre el servidor Next: `localhost` solo sirve si la API está en el mismo host. En contenedor usar el hostname del backend; no poner tokens ni secretos en `NEXT_PUBLIC_*`.
